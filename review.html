A guided tour of a small local agent platform: how a typed function becomes durable work, how a crash becomes a retry, and how independent workers become a workflow.

Node ≥ 24ES modules + tsxAt-least-once deliveryOne local platform

01 / Start with the problem

A function call forgets. A task remembers.

An ordinary function runs inside your process. If the process dies, its local state and unfinished work disappear. This library records the work first, then gives it to a replaceable process. SQLite remembers what is still owed.

An “agent” here is a named worker offering typed tasks. It can call a language model, but the runtime does not require one, manage a conversation, or supply an autonomous reasoning loop. A task can simply transform text or write a file.

Identity is durable

Agent = stable name, UUID, stored config, inbox, and private files. Registering the same name on the next boot finds the same identity.

Execution is disposable

Runtime = one child process, with a PID and incarnation number. A replacement gets a new incarnation while keeping the agent’s identity.

Work is recorded

Task = a durable inbox item. Its ID stays the same across retries. Its status and result outlive the process that executed it.

Keep these separateWhat each means
Definition → agentA definition is code and schemas. An agent is a persistent identity using that code. Several agents can use one definition.
TaskRef → TaskHandleA ref names an operation, such as writer.task("save"). A handle identifies one execution returned by send().
Inbox → dispatcherThe inbox stores pending obligations. The dispatcher delivers them when a runtime is running and available.
WorkflowRef → WorkflowHandleA ref is a registered recipe. A handle is one persisted run of that recipe.
The central design rule: code defines behavior; the database stores progress. Register agent modules, workflow definitions, listener targets, and restart policies on every boot.

02 / Get something running

From zero to a durable note

In the repository root, install dependencies and try the complete library showcase. The package exports TypeScript source directly; there is no build step. Use Node 24 or newer and tsx.

npm install
npm run demo:newsroom

# Development checks
npm run typecheck
npm test

The newsroom demo intentionally recreates examples/newsroom/data each run. It demonstrates offline workers, a crashed editor, file sharing, and fallback review. For a minimal example you can keep, create these two files at the repository root.

notes.agent.ts — the worker’s definition

import { z } from "zod";
import { defineAgent } from "mini-agent-runtime";

export default defineAgent(import.meta.url, {
  tasks: {
    save: {
      input: z.object({
        name: z.string().regex(/^[a-z0-9-]+$/),
        text: z.string(),
      }),
      async run({ name, text }, ctx) {
        ctx.log(`Saving on attempt ${ctx.attempt}`);
        return ctx.fs.write(`~/notes/${name}.txt`, text);
      },
    },
    read: {
      input: z.object({ path: z.string() }),
      run: ({ path }, ctx) => ctx.fs.read(path),
    },
  },
});

review-demo.ts — the platform application

import { createPlatform } from "mini-agent-runtime";
import notes from "./notes.agent.js";

await using platform = createPlatform({ dataDir: "review-data" });
const writer = platform.agent("writer", notes);

await platform.start();

const save = writer.task("save");
const task = save.send(
  { name: "hello", text: "A process can go away. This note stays." },
  { idempotencyKey: "first-note-v1" },
);

const saved = await task.result();
console.log(saved); // { path: "agents/<uuid>/notes/hello.txt", bytes: ... }
console.log(await writer.send("read", { path: saved.path }).result());
console.log(task.info().status); // "completed"
// await using closes the platform at the end of this module.
npx tsx review-demo.ts

The .js import follows this repository’s NodeNext convention; tsx resolves the TypeScript source. On the second run, the same name finds the same agent and the same idempotency key returns the original save task. Change the key or omit it to request new work.

  1. defineAgent packages task schemas, handlers, and the module URL.
  2. platform.agent binds that definition to a durable name.
  3. start recovers old work before starting runtimes.
  4. send validates and stores input synchronously, returning a handle.
  5. result waits for durable completion or rejects on final failure.

The public API wires services together and preserves TypeScript inference. The kernel owns persistence and scheduling. The generic runtime host knows how to load and execute an agent, but never reads the inbox directly.

04 / Trace one request

A task’s journey, including the unhappy paths

The dispatcher normally allows one outstanding delivery per agent, selecting the oldest pending item. Different agents can work concurrently. Choose a path below to follow the same durable task through the system.

pending → claimed → completed
  1. Validate: TaskRef checks the input schema in the caller.
  2. Persist: Inbox stores the raw input and returns a stable task ID.
  3. Claim: Dispatcher records the runtime incarnation and increments attempts.
  4. Execute: Host validates input again, then invokes the handler.
  5. Commit: TASK_COMPLETED becomes the stored result, if the incarnation still owns the claim.
  6. Notify: Settlement wakes result() waiters and workflow reconciliation.

Why “at least once” matters

Imagine a handler sends an email, then crashes before its completion is recorded. The inbox still owes the task, so the replacement runs it again. Durable delivery cannot by itself make that email happen exactly once.

Two separate deduplication tools: a caller’s idempotencyKey prevents duplicate inbox items for the same recipient. A handler’s stable ctx.taskId can be passed to an external service to deduplicate effects across deliveries. A new workflow fallback assignment creates a new task ID; effects shared across candidates may need a workflow-level key.

Inbox deduplication is scoped to the recipient agent, not the task name. Reusing a key for another operation on that agent returns the original item; it does not update the payload. Workflow start keys are scoped to the workflow name.

05 / Design for interruption

Retries and restarts solve different problems

Retry a task

The inbox counts deliveries. A normal handler error returns the item to pending until maxAttempts is reached (default: 3). The same runtime can execute the next attempt. Handler-error retries have no exponential backoff.

Restart a runtime

The supervisor replaces a crashed process according to its agent policy. Restarts use exponential backoff and a sliding-window cap. A deliberate stop does not trigger automatic restart.

FailureWhat happens
Invalid send inputTaskInputError is thrown before anything is enqueued.
Handler throws a normal errorRetry while delivery budget remains; otherwise settle failed.
PermanentError or FsDeniedErrorFail this task immediately. A containing workflow may still try its next candidate.
Unknown task / invalid host inputThe runtime rejects it as non-retryable.
Runtime exits mid-taskRelease its claims to pending, or fail exhausted items. Crashes count toward task attempts too.
Restart cap reachedRuntime becomes given-up. Manual agent.start() clears supervision history and tries again. Pending work may remain waiting.
Platform restartsClose stale runtime rows, release old claims, reconcile workflows, start scanning, then start autostart agents.

Incarnation fencing prevents a reply from an old process from completing a claim owned by its replacement. Inbox completion and failure updates require the matching claiming incarnation.

Timeouts do not cancel handlers. The request timeout defaults to 5 seconds. The supervisor rejects the wait but leaves the process running, so a retry can overlap a still-executing handler. Correlation uses task ID, not a unique delivery ID; incarnation fencing does not distinguish timed-out attempts in the same process. Set a suitable request timeout and make effects idempotent, especially for model or network calls.

Recovery resumes durable tasks and workflow steps; it does not restore a JavaScript stack or continue a handler at its interrupted line. Waiting promises are also local to the current process: retain IDs and create new handles after a restart.

06 / Authoring agents

Types at the call site, validation at the boundary

Export defineAgent(import.meta.url, { config?, tasks }) as the module’s default export. Each task has an input Zod schema and a run(input, ctx) handler. The return value determines the output type; there is no declared output schema or runtime output validation.

One module, two processes. The application imports the definition to register it; each host imports it to execute tasks. Keep top-level code free of startup side effects. Put platform bootstrapping in a separate module.

The handler’s context

FieldUse it for
ctx.agent{ id, name, incarnation }: identity plus current process generation.
ctx.taskIdThe stable inbox ID across deliveries. Useful for external idempotency.
ctx.attemptDelivery number, starting at 1.
ctx.configSchema-parsed configuration, or undefined with no config schema.
ctx.log(text)Runtime console output prefixed with identity and PID; enable runtime.inheritStdio to see it in the parent.
ctx.fsAsync read, write, list, share, and revoke through the platform.

Raw input versus parsed input

TaskInput<D, K> is the schema’s input type; the handler sees its output type after defaults and transforms. send() validates but stores the raw value, allowing the runtime to parse the original input rather than transform an already-transformed value. Keep schemas deterministic and free of effects: parsing happens more than once.

// A task schema can accept a string and give its handler a number.
input: z.object({ count: z.string().transform(Number) })
// caller: { count: "3" }      handler: { count: 3 }

// Type helpers exported by the package:
type SaveInput = TaskInput<typeof notes, "save">;
type SaveOutput = TaskOutput<typeof notes, "save">;
type Names = TaskNames<typeof notes>;

Config belongs to identity; parsed config belongs to a runtime

Declare a config schema in the definition and supply { config: ... } in platform.agent(). Registration validates before changing stored state. Omitting config preserves the stored value; without prior config, validation sees {}. Raw config is persisted, then parsed at host startup. A changed value takes effect on the next start or restart. A path in config does not grant permission to that path.

Keep task inputs, results, config, and workflow outputs JSON-compatible. They cross Node IPC and JSON storage: classes, functions, dates, and big integers do not retain arbitrary JavaScript semantics. A handler returning undefined is stored as null, even though the inferred return type can be void.

07 / Shared data without shared ownership

Every platform file operation has an identity

review-data/
├── platform.db
├── agents/<agent-id>/     ← ~/ inside that agent
└── shared/
    ├── documents/
    └── artifacts/

Paths are logical, POSIX-style paths relative to the data root. An agent implicitly owns agents/<its-id>/**. Shared paths are closed until the platform grants access.

// Platform code: authority to grant shared access.
writer.grant("shared/documents/in", "read");
writer.grant("shared/artifacts/out", "write");

// Handler code: authority to share its own files.
const saved = await ctx.fs.write("~/report.txt", "Approved");
await ctx.fs.share(saved.path, reviewerId, "read");
// Later: await ctx.fs.revoke(saved.path, reviewerId);
  • A directory grant covers its subtree. The most specific matching grant wins; write access also allows reads.
  • An agent may share or revoke paths it owns, not re-grant arbitrary shared paths just because it can read them.
  • The platform derives the caller’s identity from the IPC channel, not from a field the runtime supplies.
  • Paths are normalized before authorization; root escapes and symlink traversal are rejected. Decisions are audited.
  • Writes use a temporary file followed by rename so readers see the old or new contents. Scans and listings skip *.tmp files.
This is a cooperative permission system. Child processes run as the same OS user and can import node:fs directly. These grants protect operations through ctx.fs; they are not an OS sandbox for hostile code. File writes and SQLite updates are also separate persistence boundaries.

08 / Compose durable work

A workflow is a persisted sequence of task assignments

Each step sends an ordinary inbox task. When that item settles, workflow reconciliation advances the run. A platform restart can catch up by reading the same stored statuses; the workflow does not depend on an uninterrupted chain of promises.

Using writer and the definition from the first example, register this workflow before platform.start(). Start the run after startup.

const noteAndRead = platform.workflow("note-and-read")
  .input(z.object({ name: z.string(), text: z.string() }))
  .step("save", writer.task("save"), ({ input }) => input)
  .step("read", writer.task("read"), ({ steps }) => ({
    path: steps.save.path,
  }))
  .output(({ steps }) => ({
    path: steps.save.path,
    text: steps.read,
  }))
  .build();

// After await platform.start():
const run = noteAndRead.start({ name: "memo", text: "Hello" });
const output = await run.result(); // { path: string, text: string }
const saved = run.step("save");
if (saved.status === "completed") console.log(saved.result.path);
console.log(run.task("read")?.info().attempts);
const reattached = noteAndRead.run(run.id);

Add import { z } from "zod" to the application for this example. Step names must be unique, and a workflow needs at least one step. Each input function sees parsed workflow input, earlier step outputs, and workflow.id. Without .output(), the result is the last step’s output.

Fallback is sequential, not a race

// With separately registered junior and senior agents:
.step("review", [junior.task("review"), senior.task("review")],
  ({ steps }) => ({ path: steps.save.path }))

The first candidate gets the step. Only when its task finally fails does the next candidate get a new task. An offline candidate’s task waits in its inbox; unavailability alone does not trigger fallback. The assignment counter starts at 1. run.task(name) points to the current candidate’s task.

Candidates may be different task names, but their TypeScript input types must agree. The computed input is validated against every candidate schema, and the output type is their union. Input mapping runs again on reassignment, so keep it pure and deterministic. A mapping error fails the workflow; it is not a handler retry.

Recovery and definition changes

The run stores its definition name and a fingerprint of step order, names, task names, candidate agent names, and the presence of an output projection. Missing code leaves a running workflow skipped until registered. A changed fingerprint fails a running workflow with “definition changed.”

The fingerprint does not hash handler code, schemas, mapping functions, or the projection’s body. Reusing a name after changing that logic can affect unfinished runs. This is shape checking, not complete code versioning.

ref.run(id) verifies the name and fingerprint before returning a typed handle. platform.workflowRun(id) gives untyped inspection. run.input() returns the original raw input; step functions see parsed input. Output projections run in the platform process, should be synchronous and pure, and fail the run if they throw; their result is persisted.

09 / Turn files into work

A listener remembers what it has seen

Listeners recursively scan a logical directory and compare file modification time and size with a persisted snapshot. They can notice files that arrived while the agent—or the platform—was offline, provided those files remain visible when scanning resumes.

// Register before platform.start(), using the writer from the first example.
writer.grant("shared/documents/in", "read");
const incoming = platform.listen("incoming-notes", {
  dir: "shared/documents/in",
  events: ["created", "modified"],
  includeExisting: true,
}).send(writer.task("read"), file => ({ path: file.path }));

const nextTwo = incoming.take(2); // subscribe before files arrive
// After startup and two matching file events:
const tasks = await nextTwo;
const texts = await Promise.all(tasks.map(task => task.result()));

Send a task

.send(taskRef, mapper) requires the target agent to have read access to the watched directory. Access is checked at registration and on every scan.

Start a workflow

.startWorkflow(ref, mapper) is platform-owned and does not require an agent grant to scan. Tasks in that workflow still need their own file permissions.

  • Default events: ["created"]. Existing files are baselined on first registration unless includeExisting: true.
  • The same name preserves its snapshot on later boots. Changing its directory resets the snapshot. Register its target function again every boot.
  • Defaults: a 1,000 ms scan interval and a 100 ms mtime settling delay. There is no deletion event; disappeared files are forgotten.
  • Successful target creation and snapshot advancement share a database transaction. An idempotency key based on listener name, event, path, and mtime guards repeated delivery of the observed version.
  • A mapping or target error emits listener.error and still marks that version seen. It is not automatically retried every scan; a subsequent change can fire again.
  • onFire() and take(n) observe future firings in this process. They do not replay history. take(n) waits for handles, not task completion, and has no timeout.

This is snapshot polling, not a complete filesystem event journal. A create-and-delete between scans can be missed; metadata-based detection is not content hashing. Keep durable input files available until processed.

Source: scan and transaction behavior · listener edge cases

10 / Operate the platform

Register first. Recover second. Execute third.

  1. Create: createPlatform() opens/migrates the database, creates filesystem roots, and wires services. It does not start runtimes or scanning.
  2. Register: agents, grants, workflows, listeners, and event subscribers. Duplicate names of the same kind in one platform instance are rejected.
  3. Start: recover runtime records → release stale claims → reconcile workflows → start listeners → start autostart agents concurrently.
  4. Work: send tasks, start workflows, inspect handles. Sending to an offline agent is valid; work waits.
  5. Close: stop scanning, stop runtimes, let final settlement notifications run, close SQLite. close() is safe twice; await using invokes it automatically.

start() is a one-time lifecycle transition. If any autostart fails, it rejects after collecting failures, while successfully started agents remain running. Close in cleanup or fix and manually start the failed agent; do not call platform.start() again. Shutdown is not a drain-all-tasks operation: unfinished work remains recoverable.

Agent manual start/restart requires platform startup first. Agents registered after startup autostart asynchronously by default; failure emits agent.start-failed. Workflows registered after startup trigger catch-up for running workflows.

11 / Explain what happened

Use handles for state, events for a live timeline

const unsubscribe = platform.events.onAny((name, event) => {
  console.log(name, event);
});

platform.events.on("task.settled", event => {
  console.log(event.agent.name, event.taskId, event.status);
});

// Durable inspection:
writer.inbox("failed");
writer.history();
platform.task(taskId).info();
platform.workflowRun(runId).events();

// Later:
unsubscribe();

on, once, and onAny return unsubscribe functions. Public events carry AgentRef objects with both id and name. Subscriptions are synchronous, in-memory notifications: keep callbacks quick and avoid throwing. The public event stream is not a persisted, replayable log; workflow transition history is stored separately.

When something seems stuck

My task’s result() never resolves.

Inspect task.info() and the agent’s runtime(). A pending task may belong to an offline, deliberately stopped, or given-up agent. Start that agent. A waiting promise has no built-in deadline or cancellation. If the platform was restarted, reattach by task ID in the new platform instance.

The listener sees no work—or take(2) waits forever.

Check listener.info(), whether scanning has started, the logical directory, read grants for a task target, and whether pre-existing files were baselined. Subscribe before files arrive. Inspect listener.skipped and listener.error; a bad mapping consumes that observed file version.

A workflow does not reach its fallback.

Inspect run.step(name) and run.task(name)?.info(). Fallback waits for terminal task failure, not merely an offline runtime or an individual failed attempt. A stopped agent can hold pending work indefinitely.

A change to code or config did not behave as expected.

Config is parsed at runtime startup, and a module is loaded into its process. Restart for new runtime config/code. Register all definitions on the next platform boot. Workflow fingerprints detect structural changes but not changes to function bodies or schemas.

14 / Know the edges

Small enough to understand, with explicit limits

This codebase is a local teaching platform with meaningful durability boundaries. Treat one platform process as the owner of a database and data root: recovery assumes old claims are stale. WAL does not turn this into a coordinated multi-platform scheduler.

Implemented today

Named identities and config; supervised processes; durable inboxes; bounded retries; filesystem grants and audit; persisted file listeners; sequential workflows with fallback; typed handles, outputs, and inspection.

Still future work

Persistent sessions and conversations; agent-originated messaging and durable waits; human approvals; general event sources; cancellation and branching; full definition versioning; OS isolation; distributed operation and app hosting.

There is no built-in exactly-once execution, transactional external effect, output schema validation, or restoration of in-memory handler progress. The actor analogy explains identity and message delivery; it does not imply a full Erlang runtime or hostile-code isolation.

Try these three small experiments

  1. Offline delivery: set autostart: false, start the platform, send a task, inspect its pending state, then call writer.start().
  2. Deduplication: send two different payloads to the same agent with one key. Compare their handle IDs and inspect which input was retained.
  3. Durable reattachment: save a task or run ID, close the platform, create a new instance with the same data directory, register the same definitions, start, and inspect the recovered handle.
